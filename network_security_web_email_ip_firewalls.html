MOD — 01

Web Security & SSL

Web Security Considerations

The Web is a client/server application over TCP/IP, but it adds new risks (Stallings §16.1):

  • Two-way: servers are attackable from the Internet.
  • Visible outlet: subverted servers damage reputation and money.
  • Complex software: hides many security flaws.
  • Launching pad: a compromised server exposes the whole internal network.
  • Untrained users: casual clients lack tools and awareness.

Passive attacks: eavesdropping, unauthorised access to restricted data. Active attacks: impersonation, message alteration in transit, site defacement. Threats lie at the server, browser or network traffic; this chapter addresses traffic security.

ConfidentialityEavesdropping, theft of server/client data, network configuration infoLoss of information and privacyEncryption, Web proxies

SSL Architecture

SSL (Netscape, SSLv3) uses TCP for a reliable end-to-end secure service. It is two layers: the Record Protocol (base layer) carrying three upper protocols — Handshake, Change Cipher Spec, Alert — plus HTTP.

Connection vs Session

Connection: a transient peer-to-peer transport; every connection belongs to one session. Session: an association between client and server created by the Handshake Protocol; defines shared cryptographic parameters reused across connections to avoid costly renegotiation.

Session stateConnection state
Session identifier, peer certificate (X.509v3), compression method, cipher spec, 48-byte master secret, is-resumable flagServer/client random, server/client write MAC secret, server/client write key, IVs (CBC), sequence numbers (reset to 0 on change_cipher_spec; max 264−1)

SSL Record Protocol

Provides confidentiality (shared key encryption) and message integrity (MAC). Sender steps:

  1. Fragment into blocks ≤ 214 bytes.
  2. Compress (optional, lossless; default null).
  3. Add MAC over compressed data.
  4. Encrypt compressed data + MAC (block cipher: pad to block multiple + pad-length byte).
  5. Append header: Content Type (8), Major Ver (8), Minor Ver (8), Length (16).
MAC = hash( MAC_write_secret ‖ pad_2 ‖ hash( MAC_write_secret ‖ pad_1 ‖ seq_num ‖ type ‖ length ‖ fragment ) )
pad_1 = 0x36 repeated 48× (MD5) / 40× (SHA-1); pad_2 = 0x5C, same counts
Exam Note

SSLv3 concatenates the pads; HMAC XORs them. Padding example: 58-byte data + 20-byte SHA-1 MAC + 1 length byte = 79 → add 1 pad byte for 8-byte blocks. Content types: change_cipher_spec, alert, handshake, application_data. Ciphers: AES, IDEA, RC2-40, DES-40, DES, 3DES, Fortezza; RC4-40/128 (stream).

Change Cipher Spec & Alert Protocols

  • Change Cipher Spec: one byte (value 1); copies the pending state into the current state.
  • Alert: 2 bytes — level (warning 1 / fatal 2) + code. Fatal: unexpected_message, bad_record_mac, decompression_failure, handshake_failure, illegal_parameter. Others: close_notify, no_certificate, bad/unsupported/revoked/expired/unknown certificate.

Handshake Protocol (four phases)

Message format: Type (1 byte), Length (3), Content. Used before any application data.

PhaseMessagesPurpose
1. Security capabilitiesclient_hello → server_helloVersion, Random (32-bit timestamp + 28 random bytes; nonces against replay), Session ID, CipherSuite list, compression. Server picks one suite; version = lower of client/server.
2. Server auth & key exchangecertificate, server_key_exchange, certificate_request, server_doneServer certificate chain (not needed for anonymous DH); key exchange params signed over hash(ClientHello.random ‖ ServerHello.random ‖ params).
3. Client auth & key exchangecertificate, client_key_exchange, certificate_verifyRSA: client sends 48-byte pre-master secret encrypted with server public key. DH: client public value. certificate_verify proves private-key ownership.
4. Finishchange_cipher_spec, finished (both sides)Switch to new CipherSpec; finished = hash over master secret and all handshake messages, verifying key exchange/authentication.

Key exchange methods

  • RSA: secret encrypted with receiver’s RSA public key.
  • Fixed DH: DH parameters in CA-signed certificate; fixed secret between peers.
  • Ephemeral DH: signed one-time DH keys; most secure (temporary, authenticated).
  • Anonymous DH: no authentication; vulnerable to man-in-the-middle.
  • Fortezza: Fortezza scheme.
master_secret = MD5(pms ‖ SHA('A' ‖ pms ‖ ClientRandom ‖ ServerRandom)) ‖ MD5(pms ‖ SHA('BB' ‖ …)) ‖ MD5(pms ‖ SHA('CCC' ‖ …)) → 48 bytes
key_block generated the same way from master_secret → client MAC secret, server MAC secret, client key, server key, client IV, server IV

HTTPS (HTTP over SSL/TLS, RFC 2818)

  • URL begins https://; uses port 443 (HTTP uses 80).
  • Encrypted: requested URL, document contents, form contents, cookies (both directions), HTTP headers.
  • Connection initiation: HTTP client also acts as TLS client; sends ClientHello, completes handshake, then all HTTP data travels as TLS application data.
  • Three levels of awareness: HTTP connection, TLS session (supports many connections), underlying TCP connection.
  • Closure: each side sends TLS close_notify; HTTP may signal Connection: close. A TCP close without close_notify may indicate attack, so the client should warn.
Exam Pitfall

HTTPS is not a new protocol; it is HTTP layered on SSL/TLS. Security rests on certificate validation: anonymous DH offers no authentication and is open to man-in-the-middle.

MOD — 03

Email Security: PGP

Overview

PGP (Phil Zimmermann) gives confidentiality and authentication for email and file storage using the best available algorithms: RSA/DSS/Diffie-Hellman (ElGamal), CAST-128/IDEA/3DES, SHA-1. It is free, platform-independent and not controlled by any government or standards body.

ServiceAlgorithmsHow
Digital signatureDSS/SHA or RSA/SHASHA-1 hash of message encrypted with sender’s private key
Message encryptionCAST-128 / IDEA / 3DES + RSA or DH(ElGamal)One-time session key encrypts message; session key encrypted with recipient’s public key
CompressionZIPAfter signing, before encryption
E-mail compatibilityRadix-64Binary → printable ASCII

Operation

Authentication

  1. Sender creates message.
  2. SHA-1 → 160-bit hash.
  3. Hash encrypted with sender’s private key (RSA) and prepended.
  4. Receiver decrypts hash with sender’s public key.
  5. Receiver recomputes hash and compares; match = authentic.

Confidentiality

  1. Sender generates message and random 128-bit session key.
  2. Message encrypted with CAST-128 (64-bit CFB mode).
  3. Session key encrypted with recipient’s public key, prepended.
  4. Receiver recovers session key with private key and decrypts.
Both services:  E( Ks , Z( M ‖ E(PRa, H(M)) ) ) ‖ E(PUb, Ks)  → sign, compress, encrypt, then encrypt key
Why symmetric + public key?

Symmetric ciphers are much faster; the public-key step solves session-key distribution (no handshake possible in store-and-forward email); one-time keys limit exposure per key.

Order matters: sign → compress → encrypt

Sign before compression so the signature can be verified against stored plaintext and because ZIP is non-deterministic across implementations. Encrypt after compression because compressed text has less redundancy, making cryptanalysis harder.

Radix-64

3 octets → 4 ASCII characters plus a CRC; expands data by 33%, but ZIP (~2:1) gives net ≈ 0.665×, still about one-third smaller.

Keys, Key IDs & Key Rings

  • Four key types: one-time session keys, public keys, private keys, passphrase-based symmetric keys.
  • Session key generation: CAST-128 in CFB with keystroke-timing-derived randomness (ANSI X12.17 style).
  • Key ID = least significant 64 bits of public key (PUa mod 264); identifies which key decrypts the session key or verifies a signature.

Message format

Session key component (recipient key ID + encrypted Ks), Signature component (timestamp, sender key ID, leading two octets of digest, encrypted SHA-1 digest), Message component (filename, timestamp, data). Detached signatures are supported (separate logs, executables, multi-party contracts).

RingEntriesNotes
Private-key ringTimestamp, Key ID, public key, encrypted private key, User IDPrivate key encrypted with CAST-128 using SHA-1(passphrase) as key; passphrase then discarded
Public-key ringTimestamp, Key ID, public key, OWNERTRUST, User ID, KEYLEGIT, signatures, SIGTRUSTOthers’ public keys; indexed by User ID or Key ID

Public-Key Management & Web of Trust

Protecting public keys from tampering is the “Achilles heel” of public-key cryptography: a forged key lets an attacker forge signatures and read messages. Approaches: get key physically; verify the fingerprint (SHA-1 digest) by phone; obtain from a trusted introducer; obtain from a certifying authority.

  • OWNERTRUST: user-assigned trust in key owner as a signer (unknown, untrusted, marginal, complete, ultimate).
  • SIGTRUST: cached owner trust of each signer.
  • KEYLEGIT: computed by PGP; complete if one ultimate signature, or weights reach 1 (1/X per always-trusted, 1/Y per usually-trusted signature).
Revocation

Owner issues a key revocation certificate signed with the corresponding private key and disseminates it widely. An attacker with the private key could also revoke, but that harms the attacker too, so it is unlikely.

MOD — 04

IP Security (IPsec): Modes

Overview & Services

IPsec encrypts and/or authenticates all traffic at the IP level, for IPv4 and IPv6. Uses: branch-office VPNs, secure remote access, extranet/intranet links with partners, safer e-commerce. Benefits: strong perimeter security in firewall/router, resistant to bypass, below TCP/UDP so transparent to applications and users.

  • RFC 4301 services: access control, connectionless integrity, data-origin authentication, replay rejection, confidentiality, limited traffic-flow confidentiality.
  • Protocols: AH (authentication; deprecated, ESP covers it) and ESP (encryption + optional authentication). IKE handles key management.

Transport vs Tunnel Mode

Transport modeTunnel mode
ProtectsPayload of IP packet (TCP/UDP/ICMP segment)Entire original IP packet, as payload of a new outer IP packet
Typical useEnd-to-end between two hostsAt least one end is a security gateway (firewall/router): VPNs
HeadersOriginal IP header kept, readable by routersNew outer header (gateway addresses); inner header hidden
AHAuthenticates payload + selected IP header fieldsAuthenticates entire inner packet + selected outer header fields
ESPEncrypts payload (and IPv6 ext headers after ESP)Encrypts entire inner IP packet
ESP + authAuthenticates payload, not IP headerAuthenticates inner packet (ESP header + ciphertext)
Hosts need IPsec?YesNo; gateway does the work
Transport ESP (IPv4): [Orig IP hdr][ESP hdr][ TCP | Data | ESP trailer ][ESP auth] ← encrypted: TCP..trailer
Tunnel ESP: [New IP hdr][ESP hdr][ Orig IP hdr | TCP | Data | ESP trailer ][ESP auth] ← encrypted: orig IP..trailer
Tunnel example

Host A sends packet to B; A’s gateway sees policy match, encapsulates it with an outer header (gateway → gateway); routers examine only the outer header; B’s gateway strips it and delivers the inner packet to B.

Security Associations & Policy

An SA is a one-way relationship; identified by SPI (32-bit, local significance), destination IP address and security protocol (AH/ESP).

  • SAD: SPI, sequence counter, overflow flag, anti-replay window, AH/ESP info (algorithms, keys, lifetimes), SA lifetime, mode (tunnel/transport/wildcard), path MTU.
  • SPD: selectors (remote/local IP, next-layer protocol, name, ports) map traffic to an SA with action PROTECT, BYPASS or DISCARD.
  • Outbound: match selectors in SPD → find SA/SPI → apply AH/ESP.

ESP Format & Anti-Replay

  • Fields: SPI (32), Sequence Number (32), Payload Data (variable, may include IV), Padding (0–255), Pad Length (8), Next Header (8), ICV (optional integrity check).
  • Order: encrypt first, then compute ICV, so bogus/replayed packets are rejected before decryption (reduces DoS impact).
  • Anti-replay: sender counter starts at 0 (first packet = 1) and must not wrap past 232−1. Receiver keeps window W = 64 with right edge N. In-window and new → check MAC, mark. Right of window and valid → advance window. Left of window or authentication fails → discard (auditable).

Combining SAs & IKE

  • SA bundle: transport adjacency (AH + ESP on same packet, one level) or iterated tunneling (multiple nested tunnels).
  • IKE: manual or automated key management; IKEv2 (formerly ISAKMP/Oakley) refines Diffie-Hellman with authentication to defeat man-in-the-middle.
MOD — 05

Firewalls

Characteristics

A firewall sits between the premises network and the Internet as a single choke point for security and auditing (defense in depth).

Design goals

  1. All traffic in and out must pass through the firewall.
  2. Only authorised traffic per local security policy is allowed.
  3. The firewall itself is immune to penetration (hardened/trusted system).
ControlMeaning
ServiceWhich Internet services may be accessed (by IP, protocol, port; proxy; or hosted servers)
DirectionDirection in which requests may be initiated
UserAccess depends on which user (needs secure authentication, e.g. IPsec)
BehaviorHow services are used (spam filtering, partial web access)
Capabilities vs Limitations

Can: single choke point, block vulnerable services, defend against IP spoofing/routing attacks, monitor/audit events, host NAT and logging, host IPsec VPN.
Cannot: stop attacks that bypass it (dial-out, modems), fully stop insider threats, protect against insecure wireless LANs, stop infected laptops/portable media brought inside.

Types of Firewalls

TypeLayer / works byStrengthsWeaknesses
Packet filteringRules on source/dest IP, ports, protocol, interface; forward or discardSimple, fast, transparentNo upper-layer awareness; limited logging; no user authentication; vulnerable to spoofing and misconfiguration
Stateful inspectionPacket filter + table of established TCP connections (can track sequence numbers, inspect FTP/IM commands)Allows only replies to known sessions; avoids opening all high portsMore processing than stateless filter
Application-level gateway (proxy)Relays app traffic through proxy code; user authenticates to gatewayMost secure; per-application control and full loggingProcessing overhead (two spliced connections)
Circuit-level gatewayTwo TCP connections (inner and outer), relays segments without inspecting content (e.g. SOCKS, port 1080)Efficient; hides internal hostsDoes not inspect payload

Packet-filter policy & attacks

  • Default = discard: not expressly permitted is prohibited (conservative; preferred by business/government). Default = forward: not expressly prohibited is permitted (open organisations).
  • IP spoofing: drop outside-arriving packets with inside source address.
  • Source routing: discard packets using the option.
  • Tiny fragment: enforce minimum transport header in first fragment; discard the rest if rejected.

Basing & Configurations

  • Bastion host: hardened critical strong point hosting proxies; minimal services, per-proxy authentication, small independent proxies, full audit logs, read-only code, non-privileged execution.
  • Host-based firewall: software on a server; tailored rules, topology-independent, adds a layer.
  • Personal firewall: protects a PC; denies unauthorised remote access, can monitor outgoing malware.
  • DMZ: region between external and internal firewalls holding public servers (web, mail, DNS). Internal firewalls add stricter filtering and protect both ways.
  • VPN: IPsec in the firewall allows filtering; IPsec in a separate box behind the firewall hides the encrypted traffic from it.
  • Distributed firewalls: stand-alone and host-based firewalls under central administration.

Intrusion Detection & Prevention

Intruders

ClassDescriptionLikely origin
MasqueraderUnauthorised user exploiting a legitimate accountOutsider
MisfeasorLegitimate user misusing access or privilegesInsider
Clandestine userSeizes supervisory control to evade auditingEither

Intrusion Detection (IDS)

Prevention eventually fails, so detection is the second line of defense: fast detection limits damage, deters intruders and yields data to strengthen prevention. It assumes intruder behaviour differs measurably from legitimate behaviour, but the profiles overlap.

False positives vs false negatives

Loose rules catch more intruders but flag legitimate users (false positives); tight rules miss intruders (false negatives). The base-rate fallacy: when real intrusions are rare, even an accurate detector produces mostly false alarms, which operators then ignore.

ApproachTechniqueBest against
Statistical anomalyThreshold detection (event counts over time); profile-based (per-user metrics: counter, gauge, interval timer, resource use; models: mean/std-dev, multivariate, Markov, time series, operational)Masqueraders; needs no knowledge of vulnerabilities
Rule-based anomalyRules auto-generated from historical usage patternsDeviations from past behaviour
Rule-based penetration identificationExpert-system rules for known attacks/weaknesses (e.g. IDES, USTAT)Known penetrations; misfeasors

Audit records & distributed IDS

  • Native audit records (no extra software, may lack detail) vs detection-specific (Denning format: Subject, Action, Object, Exception-Condition, Resource-Usage, Time-Stamp).
  • Distributed IDS (UC Davis): host agent modules, LAN monitor agents and a central manager that correlates reports; must protect audit data in transit and handle differing formats.
  • Honeypots: decoy systems that divert attackers, collect activity data and keep them engaged while administrators respond; any access is suspect.

Intrusion Prevention (IPS)

Source note

Stallings 5th ed. has no dedicated IPS section; this part is standard supplementary material, not textbook text.

  • IPS = IDS detection engine placed inline, so it can actively block, drop packets, reset connections or reconfigure firewalls, while an IDS only alerts (passive).
  • Network-based (NIDS/NIPS) inspects traffic at a network point; host-based (HIDS/HIPS) monitors one host’s logs, files and system calls.
  • Detection methods: signature-based (known attacks, low false positives, misses novel) and anomaly-based (catches novel, more false positives).
  • Inline placement makes false positives costly (may block legitimate traffic) and adds latency and a possible point of failure.
